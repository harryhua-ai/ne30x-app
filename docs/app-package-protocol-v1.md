## 1. 产品边界（已确认）

首个 Web MVP 只允许经过认证且具管理员权限的使用者，从 NE301 Web 管理**可信发行方签名且验证通过**的独立 App；至少支持 hello-app V1 → V2 的安装/替换、手动执行一次、更新、卸载、状态和失败原因。更换业务 App 不能重新链接、重编或刷写主固件及基础 Web。首次经过独立授权部署通用 Host 不等于更换 App 的一部分。

首版**不**提供开放第三方不可信原生代码、普通用户自行安装、App Store、后台常驻或多 App 调度、开机自动运行、任意代码强制停止或生产级沙箱隔离。签名认证不能证明签名代码无漏洞；既有实验 Host 未证明 App 出错不会拖垮主系统。

`ne301` 独立实现平台 Host、设备验签、安装及管理 API，**不得**静态引用 `ne30x-app` 业务源码；`ne30x-app` 独立构建 App 与离线打包/验证，不得复制 NE301 私有平台实现。Host ABI 的唯一权威仍在 NE301。

### 1.1 已确认的存储故障产品原则与最小复用边界

**User 已确认的正式产品原则（2026-10-09）**：**保护已有数据优先于自动恢复便利性**。LittleFS、NVS 或上层配置读取/验证失败、介质是否为空不明时，设备不得自动格式化、擦除、恢复已知默认管理员凭据或向不明旧数据写回默认配置；应保留原始内容，报告不可用，并拒绝可能造成数据损失或未经验证的安装/执行。已有可信正常数据继续按原功能工作。**确实新空白的存储**只有在能够独立确认介质状态并获得明确授权的首次初始化操作中才可以格式化；**有意的管理格式化**亦须校验管理员权限、告知擦除范围、得到明确确认，且操作失败不得回报成功。若现有系统无法可靠区分全新与损坏介质，默认停止并等待人工确认/恢复，不为恢复自动化而擦除。这个原则是已确认的 WHAT，#37/#36 的代码实现、首次配置交互与真实设备验证仍未完成；不等于授权新的格式化动作或板卡操作。

## 2. 包的逻辑契约（A 候选语义；字节格式尚未定稿）

`.neapp` 是首版候选文件后缀。单一包包含**一份明确版本化 manifest、一份不透明的 NE301 原生 App 镜像 payload、可验证的发行方签名信息**；不得用裸 `.bin` 或仅 CRC/SHA 通过的文件冒充已受信任的安装包。

manifest 的逻辑字段如下；§2.3 已给出**160B 定长字节布局候选**，整数宽度、字节序、标识串限制均已有唯一提议。当前仍待 A 整体签署/冻结及独立跨端验收，不得把概述中旧的“编码未知”用作自行发明第二种线格式的许可：

| 逻辑字段 | v1 要求/约束 |
| --- | --- |
| `package_format_version` | 标识包容器的版本，未知重大版本拒绝 |
| `publisher_id`、`app_id`、`app_version` | 身份与版本可比较、可追溯；`publisher_id` 必须绑定到验签成功的可信身份，不能信任未经认证的自称 |
| `target_device`、`hardware_profile` | 显式声明目标 NE301 板型/资源条件；实验基线只验证 64 MiB PSRAM，32 MiB 不能默认兼容 |
| `required_host_abi` | 明示所需 ABI，现有实验基线是 `0x00010000`；不得依赖 App 端复制私有头 |
| `image_descriptor` | payload 长度、摘要与入口/镜像头一致性；必须按 NE301 权威镜像头及当前 Host 兼容约束交叉校验 |
| `required_capabilities`、`resource_bounds` | 可审计的能力要求和最大空间/运行预算；当前 Host 仅开放 `log`、`tick_ms`，未声明能力不得静默升级 |
| `publisher_key_sha256`、签名信息 | manifest 候选仅含受控发行方公钥的 SHA-256 身份指纹；算法由 v1 格式唯一钉定，DER 签名字节位于**容器末尾**而不在 manifest 内；签名覆盖所有安全相关元数据并绑定完整原生镜像 |

**完整性与来源认证分离**：payload 摘要/镜像头 CRC 只检出损坏，不能证明可信来源。§2.2–§2.5 已固定一组**待最终冻结的精确候选**：容器字节序、manifest、签名原文、P-256/DER/SPKI 与非生产软件黄金样本。待定分两层：**P2 协议冻结之前**由 A 关闭字段/编码/信任语义歧义并审定可复核的主机侧向量和已知设备事实；**P3/P4 实施期间及验收时**各自消费冻结向量，证明独立工具和设备端验签、资源/恢复边界。不能要求尚未 READY 的 P3/P4 先交付结果才允许冻结它们所依赖的 P2；也不能把候选主机测试当作设备 PASS。

### 2.1 数字签名算法与编码（#32 离线证据支持；随本规范集成后生效）

[NE301 #32 / PR #33](https://github.com/harryhua-ai/ne301/pull/33#issuecomment-6074823899) 的整改 Candidate `8a8bd77acb8a3f4b19dda14df042632cf7fb01ba` 已经 A 对 **离线调查本身** 作 exact-SHA ACCEPTED；**PR 尚待规范 `ght` 机械谓词识别、合并与 Issue 完成**。调查使用固件仓库同源 mbedTLS 3.6.4 的现行配置，在 Apple clang/macOS 上关闭硬件 ALT 后进行软件路径编译、OpenSSL 互操作与 22/22 正常/拒绝测试；另通过故意失败测试证明 `make test` 会非零退出。这不代表 STM32 目标镜像已完成验签链接，更不代表设备 PKA/签名包互操作已证明。

- **签名算法首选**：对约定的精确签名原文计算 SHA-256，再用 **ECDSA over secp256r1（P-256）** 验证。原因是现有固件配置开启相应模块，设备 `mbedtls_ecdsa_verify` 的 PKA ALT 分支仅支持 P-256；P-384/P-521 虽可能出现在库配置中，但不是当前设备可承诺的验签候选。本候选**不增加单独算法 ID**：版本 1 的 magic 唯一绑定 SHA-256 / ECDSA P-256 / DER / SPKI；任何其它或未知容器版本直接拒绝。实现端不得自行协商/降级算法，直到另版协议经 A 授权。
- **签名编码首选与 A 已收敛的候选规则**：签名为一个**严格、完整消费的规范 DER** `ECDSA-Sig-Value`，内含两个正整数 `r,s`，且各自须位于 P-256 合法范围 `1 <= r,s < n`；拒绝 BER 非最短整数/长度、负值、零值、越界、截断、附加字节或第二个 ASN.1 对象。**v1 不额外要求 low-S 归一化**，避免为同一合法消息强制引入与标准 ECDSA 验签不同的自定义规则；签名字节本就可能不同，内容幂等身份固定为 `SHA-256(TBS)`。这只是 A 的安全编码候选决策，不代表设备 mbedTLS/PKA 已严格拒绝这些负例；主机和设备实现须分别以正负样本证明 DER parser 的具体行为。
- **信任公钥首选**：由**受控 Host 构建内置**的单一发行方 P-256 公钥，优先规范为 SubjectPublicKeyInfo (SPKI) DER；Spike 的独立公钥解析验证了该候选在 host 侧互操作。最终生产密钥来源、构建注入、密钥指纹/发行者映射、撤销与 Host 更新策略必须另审；上传包即使携带公钥也不得因此自授信。
- **签名边界已有候选、尚未冻结**：§2.2 定义候选前缀、精确 TBS 签名原文与 DER 尾段，§2.3 定义候选 manifest/长度约束，§2.4 给出受源码支持的逻辑型号值与硬件证据缺口。冻结前须由 A 审定固定的完整黄金包、字节摘要和可独立执行的主机端结构/密码学负向向量；设备端和 P3 工具的**独立跨端校验在各自获得授权后执行**，不得倒置为冻结前置。**在此之前，P3/P4 不得各自发明兼容格式。**

**安全性质边界**：上述只解决相对既定可信 Host 的包发行来源验证。#27/#32 均未证明 Host 自身的 OTA 验签、硬件可信启动、管理员凭据保护、设备 PKA 实际运行、内存隔离和共享 LittleFS 断电事务，因此算法层候选并不解除 P4 的管理准入/存储保护门槛。

### 2.2 单签名封装与签名覆盖边界（完整候选；以本规范集成为冻结门槛）

为避免 P3 打包器与 P4 验证器各自解释“签了哪些字节”，A 提出以下 **v1 二进制封装候选**。它是唯一 P2 草案的设计输入，不是新的规范权威或实施 READY；manifest 字段/签名语义和主机黄金向量须在 P2 冻结前审定；目标固件链接/PKA 真实性及设备资源的**实现验证**由后续 #29 等负责，不得在未实测时宣称已通过。

| 字节位置（从 0 起） | 候选编码 |
| --- | --- |
| `0..7` | 固定 8 字节 magic：`4E 45 41 50 50 01 00 00`（ASCII `NEAPP`、容器主版本 1、两个零保留字节） |
| `8..11` | `manifest_len`：无符号 32 位小端整数，必须正数 |
| `12..15` | `image_len`：无符号 32 位小端整数，必须至少容纳现有 32B Host 镜像头，具体执行区上限以受审设备事实与固定 Host loader 约束收紧 |
| `16..(16+manifest_len-1)` | 原样 manifest 字节（§2.3 已提出唯一 160B 定长编码**候选**，尚未冻结） |
| 紧接 manifest | 原样独立 App 镜像 `image_len` 字节，包含 **未修改的 32B Host 原生镜像头及其 payload** |
| 文件最后剩余字节 | **恰好一个** DER `ECDSA-Sig-Value`；无签名长度字段、无额外尾部、无第二签名或证书链 |

**候选的唯一签名原文**：`TBS = 文件从偏移 0 开始，连续取 16 + manifest_len + image_len 字节`。签名计算 `SHA-256(TBS)`，使用指定发行方的 ECDSA P-256 私钥生成 DER 编码签名；验签使用受控 Host 自有可信公钥，**不得**使用包自带公钥自授信。Magic/两个长度、全部 manifest 字节与原生镜像 **连同既有 CRC 字段** 都在签名覆盖内；签名本身不参加摘要，避免“签名长度反过来影响签名”的循环。magic 同时起版本与域隔离作用。签名 DER 长度由包总长减去已签名区域长度得出；设备必须要求 DER 严格完整消费剩余全部字节，绝不忽略追加数据。

**候选的校验顺序/不变量**：

- 仅允许严格 magic；对两个 `u32` 长度的加法采用溢出安全检查、按照固定上限限制 manifest/镜像/整包长度，拒绝缺少签名、截断、越界、额外尾部及零长度。§2.3 已给出明确**候选**上限，但设备 loader/可用持久空间与 DER 验签仍待证据支持，不能让 B 自定扩容或将候选视为冻结值。
- 对 manifest 必须要求**唯一编码**（禁止重复字段、多义排序、未知安全相关字段、非规范整数/字符串），且签名中的发行方键身份、App ID/版本、板型/PSRAM、Host ABI、能力/资源声明、镜像摘要和原生镜像头必须相互一致。**manifest 编码未冻结，当前不得实现互操作打包器**。
- 完成结构约束后，以当前 Host 受信任公钥验证签名，再进行设备/ABI/资源/版本检查；任一步失败，不提交、不启动 App。通过结构与签名验证本身也不表示安装成功。
- **幂等身份**优先使用 `SHA-256(TBS)`（已签名内容的摘要），同时单独记录 `SHA-256(image bytes)`；不以包含随机 ECDSA 签名 DER 的“整个文件摘要”判断同版本内容冲突。相同签名原文可以有不同但均合法的 ECDSA 签名字节；这不得导致虚假的版本冲突。
- v1 候选只支持一把受控发行方公钥、一份原生镜像、SHA-256 + ECDSA P-256/DER；未知版本/算法、未受信任密钥、与可信身份不一致的 manifest 声明必须拒绝。不得将签名认证误称硬件安全启动、原生内存隔离或安全管理员认证。

**定稿仍需的交叉证据**：§2.3 已提出 manifest 字段的精确编码与长度上限**候选**；§2.5 已保留一组本地软件验证的合成镜像签名包及部分拒绝向量。但它们尚不是从真实 hello-app 构建的 P3/P4 互操作包，也没有 STM32 设备验签、PKA、真实容量验证。待由 P3/P4 对**同一经 A 冻结**的字段规则、密钥/签名和 magic/长度/编码/尾随数据/错板/错 ABI/资源/版本冲突完成独立正负验收。#32 的固定 64B Spike 用例不等于 .neapp 的跨端验证。

### 2.3 规范 manifest 的定长编码（唯一候选；以本规范集成为冻结门槛）

为了让 MCU 解析简单且防止 JSON/CBOR 的排序、重复键和整数表示歧义，v1 **优先使用恰好 160 字节的定长二进制 manifest**（不使用自由 JSON 文本、TLV、证书链或额外扩展区域）。这使 §2.2 中 `manifest_len` 的**候选唯一合法值**为 160；它是 A 的候选选择，不是已实现或已完成设备实测的事实。所有无符号数都按小端编码，不允许标量的其它字节序或变长写法；非空保留字段不得忽略。

| 相对 manifest 的偏移 / 长度 | 候选字段 | 编码与必须核验的约束 |
| --- | --- | --- |
| `0..3` / 4B | `manifest_magic` | ASCII `NMF1`（`4E 4D 46 31`），否则拒绝 |
| `4..19` / 16B | `publisher_id` | 1–16 字节规范 ASCII 标识，右侧 `00` 填充；身份须与设备信任映射一致 |
| `20..51` / 32B | `app_id` | 1–32 字节同样的规范 ASCII 标识与 `00` 填充 |
| `52..57` / 6B | `version_major/minor/patch` | 各 `u16-le`，只作整数三段比较；无预发布、构建后缀或前导文本 |
| `58..59` / 2B | `reserved` | 必须全零 |
| `60..63` / 4B | `target_board_id` | `u32-le`；受控实验候选为既有 OTA 逻辑型号 `0x00003010`（字节 `10 30 00 00`），详见 §2.4；**不代表硬件认证** |
| `64..67` / 4B | `required_psram_mib` | `u32-le`；当前证据仅支持 64 MiB 实验板型，32 MiB 默认拒绝 |
| `68..71` / 4B | `required_host_abi` | `u32-le`；当前固定实验 ABI `0x00010000`，并须等于原生 32B 镜像头的 ABI |
| `72..75` / 4B | `required_host_caps` | `u32-le` 位掩码：bit0=`log`、bit1=`tick_ms`；其它位必须零，且声明集合须被当前 Host API 实际支持 |
| `76..79` / 4B | `required_exec_region_bytes` | `u32-le`；声明摘除 32B 原生头后 payload 的最小运行驻留空间：不得小于原生 `image_size`，也不得超过设备可用执行区。它**不能替代**整份原生文件的临时装载容量检查 |
| `80..83` / 4B | `native_file_len` | `u32-le`，须与 §2.2 `image_len` 完全相等 |
| `84..87` / 4B | `native_image_size` | `u32-le`，须等于原生 32B 头的 `image_size`，且 `native_file_len = 32 + native_image_size` |
| `88..91` / 4B | `native_entry_offset` | `u32-le`，须等于原生镜像头的 `entry_offset`，小于 `native_image_size` 且满足现有 Thumb 对齐约束 |
| `92..95` / 4B | `native_target_addr` | `u32-le`，须等于原生镜像头 `target_addr` 和当前设备 loader 的受控执行区地址 |
| `96..127` / 32B | `native_file_sha256` | 对整个原生镜像文件（含 **原样 32B 镜像头**）求 SHA-256，须恒时比较匹配；原有 CRC32 仍需独立校验 |
| `128..159` / 32B | `publisher_key_sha256` | 对受控 Host 的发行方公钥 **SPKI DER 原始字节**求 SHA-256；包中只记录标识摘要，不携带可替换信任锚 |

标识字符集候选为小写 ASCII `a-z`、数字 `0-9` 和中间 `-`；首字符须为 `a-z`，末字符为字母或数字（单字符 ID 可为单个字母），禁止 `-` 首尾、空字符串、非 ASCII、内嵌 NUL、非零右填充、大小写折叠或 Unicode 多种归一化。标识长度不得含糊：从右侧连续零填充逆向确定文本结束位置；恰好占满槽位时无零填充。未知 `publisher_id` 或其 `publisher_key_sha256` 与设备独立保存的唯一 `publisher_id → SHA-256(SPKI DER)` 映射不一致，必须拒绝。

**原生镜像交叉检查必须收紧而不能削弱 Host ABI**：包中固定 `native_file_len = 32 + native_image_size`、原生头的 `header_size = 32`、`magic = NEA1`、`format_version = 1`，并要求原生 32B 头偏移 `24..27` 的 `reserved0` **全零**；将原生 `target_addr`、`entry_offset`、`image_size`、`abi_version` 与 manifest 字段逐字比较，并运行现有 CRC32/边界检查。现有 `app_host_validate` 对 `header_size` 只要求 **至少** 32、对文件尾部不强制恰好消费，也**不检查 `reserved0`**；所以 P4 的**签名准入层必须额外执行 v1 的更严格检查**。不得改写已有 loader/ABI 宽松行为来偷换包准入证据；本条只限定新 `.neapp` v1 的签名安装边界。

**资源上限候选与证据分级**：根据 #27 的 64 MiB PSRAM PoC，原生 Host 执行区为 2 MiB；建议首版 `native_file_len` 上限不超过 `2,097,152` 字节（设备仍须以**实际** `region_size` 复核），包头 16B + manifest 160B + 严格 DER P-256 签名最多 72B，候选整个包上限为 `2,097,400` 字节。文件必须严格按 `16 + 160 + native_file_len + DER_len` 完全消费，DER_len 候选区间 8–72B，并由严格 ASN.1 解码器校验序列/整数长度、值范围与无尾随数据；若设备实际存储写入配额、解析栈或 PKA 边界不能证明支持这些值，A **先修改并重审协议上限**，不能由 B 分别自行扩容。

**运行驻留量与装载临时量分别验证**：上述 `required_exec_region_bytes` 只表示原生 payload 剥除镜像头后的运行驻留要求；当前固定 Host `app_host_read_file` 会**先将包含 32B 原生头的整份文件写入同一执行区**，再 `memmove` 去头。因此准入**同时**要求 `required_exec_region_bytes >= native_image_size`、`required_exec_region_bytes <= 当前可信执行区大小`，以及 `native_file_len <= 当前可信执行区大小`，缺一不可。§2.5 黄金包的 `required_exec_region_bytes=4B`、`native_file_len=36B` 正是这两种量的不同含义，不可把 4B 误当装载所需总容量；如后续 Host 装载流程变化，必须重新验证实际峰值占用，而不是仅凭签名中的声明放行。此规则不暗示当前设备实际执行区容量已由目标硬件确认。

**安全检查顺序**：先对不可信头和 `manifest_len` / `image_len` 作溢出安全的有限读取与结构/唯一编码检查；然后用可信 Host 本地公钥确定签名/发布者身份并完成 ECDSA P-256 验签；之后交叉验证 `native_file_sha256`、镜像头 CRC/ABI/目标地址、设备能力、容量、版本及安装状态。中间任何失败均不可创建可执行的安装记录。若设备上还存在绕过验签可直接装载任意镜像的实验 UART/裸文件入口，必须由 P4 准入阶段关闭或受控隔离。

**共享验收向量的最低矩阵（A 已生成部分主机固定样本；P3/P4 独立验收尚未 PASS）**：

| 用例 | 预期 |
| --- | --- |
| 同一合法原生镜像与规范 manifest，受信测试发行方签名 | 打包端生成、独立验证端通过；完整 TBS 十六进制与 SHA-256 须固定归档 |
| manifest 长度不等于 160、文本带非零右填充/嵌入 NUL/大写、保留字节非零 | `BAD_PACKAGE`，不得启动 |
| 版本字段及地址/长度改一个字节、图片/镜像头 CRC 自洽但 manifest 不匹配 | 结构/摘要/签名核验拒绝；不得被误认为同一包 |
| `publisher_id` 相同但 `publisher_key_sha256` 错误，或包自带其它公钥 | `PUBLISHER_UNTRUSTED`；不得自授信 |
| 原生头 `header_size > 32`、`reserved0 != 0`（头偏移 24..27）、`native_file_len != 32 + image_size`、无效 entry/ABI/target | 即使包由受信测试钥**重新签名**且验签成功，仍须拒绝为 v1；旧 loader 的宽松行为不可替代签名准入 |
| DER 截断、尾随数据、多重 DER、错误公钥、DER 编码歧义 | 全部拒绝；硬件 PKA 路径待设备验证 |
| 同一 TBS 配两个不同但都合法的 ECDSA DER 签名 | 两包的**内容身份摘要相同**，可视为相同内容的重试；须分别验证各自签名合法 |

**证据进度与缺口**：§2.5 已使用公开非生产测试标量、160B manifest 和合成 4B Thumb 载荷生成一组可验证的签名包/负例，并由主机端 Python 与独立 OpenSSL 核对。这只关闭“候选字节可形成并被软件验证”的设计证据，**不等于**设备可安装 App、由 P3 构建的 hello-app、STM32 PKA 兼容或 P3/P4 互操作 PASS。**P2 定稿门槛**是把已证实的逻辑板型/ABI/资源上限和未证的物理设备条件明确写进约束、冻结完整字节规则和主机侧正负向量；**P3/P4 的各自验收门槛**才是使用真实工具/设备消费这些已冻结输入，补足 STM32 PKA、内存/存储和故障恢复证据。不倒置依赖，也不替后续豁免证据。

**未决而非默认通过**：`target_board_id` 与实际硬件身份如何安全判别，真实设备 2 MiB 容量与 DER/PKA 边界、Host 内置密钥部署/撤销、管理员认证、存储断电提交安全，尚需独立证据；#27/#32 都没有证明这些机制的实现。这个 manifest 提议可以在 Draft 中逐字评审，但不是 P3/P4 可以据以提前编写兼容产品代码的协议冻结信号。

### 2.4 设备型号映射的证据边界（A 候选决策；部分可确定）

**已经核对的源码事实**：[NE301 实验分支 Makefile](https://github.com/harryhua-ai/ne301/blob/c97ee19b19f0055a269ebf57c9d6f1b7d7f07d6b/Makefile#L7-L14) 将 `DEVICE_MODEL ?= 0x3010` 定为既有 OTA 设备型号门槛的单一来源；它经 `-DOTA_DEVICE_MODEL=$(DEVICE_MODEL)` 编进主机固件，并写入 OTA / bundle 头。相同 [Makefile 的通用构建定义](https://github.com/harryhua-ai/ne301/blob/c97ee19b19f0055a269ebf57c9d6f1b7d7f07d6b/Makefile#L119-L126) 固定 `BOARD_PSRAM_SIZE=64`、默认 `BOARD_FLASH_SIZE=128`（后者可在编译时改为其它受支持配置）。这些是**构建模型与默认配置**，不是对板上真实外设容量的自动探测。历史 [设备证据](https://github.com/harryhua-ai/ne30x-app/blob/main/docs/evidence/device-evidence.md) 记录 STM32N657 Rev B（芯片 Device ID `0x486`）及 96MiB LittleFS 布局，但芯片 ID 本身不是 App 协议的板型 ID。

**对 v1 的最小候选映射**：§2.3 的 `target_board_id` 暂定义为固件构建采用的 **OTA 逻辑 `DEVICE_MODEL` 值**；受控实验 Host 唯一候选为 `0x00003010`，其 `u32-le` 字节为 `10 30 00 00`。它**不是**芯片 Device ID `0x486`、序列号、不可伪造的硬件身份或密钥授权来源；不可由 App 包声明来覆盖设备自己编入的型号。其它型号一律拒绝，直到有独立受审的兼容配置，不进行数字范围猜测或近似匹配。

**硬件配置须另外校验**：此候选仅适用于受控实验的 64MiB PSRAM + 128MiB NOR Flash 配置。签名包中的 `required_psram_mib=64`（字节 `40 00 00 00`）不能替代设备侧核对；同一 `DEVICE_MODEL` 若被用于另一种真实 Flash / PSRAM 组合，也**不自动**获得兼容资格。P4 准入层须使用已可信的当前 Host 构建身份、有效执行区链接地址/实际大小、现存持久化卷尺寸与可用容量进行拒绝式核对；实际板卡与固件所声明内存/分区关系未经独立核实，则仅允许离线解析/验签实验，不得宣称设备安装兼容。**本条不暗示运行时已经存在可信容量探测器**，也不授权 B 修改 OTA 设备型号系统。

**构建与状态漂移**：Makefile 明确提示修改 `DEVICE_MODEL` 后须重新 clean/build（普通 `make` 不跟踪编译参数变化，旧对象可能保留旧型号）。因此型号/PSRAM/Flash 的兼容性证据至少需要可追溯的构建选项、固件产物身份以及部署板卡的只读核对。该 evidence gate 不要求在本 Draft 阶段访问或写入设备，亦不等价于生产可信启动。

**定稿判断**：先保留该逻辑型号映射，作为 P2 规范候选而非已完成的板卡检测实现。如果后续只读设备核对或 Host 构建证据证明 `0x3010` 被多种互不兼容的板卡配置共用，A 必须在开放 P3/P4 READY 前缩窄支持范围或修订字段/型号版本；不能默认信任 signed manifest 自己的设备声明来修复这一问题。

**本项可关闭的只是“从原样 hello-app 源码得到另一工具链 ARM payload、并可被候选签名封装/主机独立验签”的局部问题。** 历史 V1/V2 原生二进制仍未拿到；设备 PKA/mbedTLS 互操作、当前 Host ABI 运行、管理员认证、信任根保护、存储事务与掉电恢复均未测试。Clang 实验编译不授权替换官方 GCC 15.2.1 构建基线，更不构成 P2 冻结或 P3/P4 READY。

## 3. 身份、版本和互操作（A 候选语义）

- 以发行者身份 + App ID 确定 App 逻辑身份；同身份的新版本才是升级，换发行者不能静默接管旧 ID。
- 成功安装应回报已验证的发行者、App ID、版本、包/镜像摘要及 ABI/板型兼容结果，供 Web 和运维核对。上传或离线打包成功均**不**代表已安装或获执行权限。
- 未知包版本、错误目标板/ABI、签名不可识别/失效、摘要不符、资源限制不满足时，**拒绝安装且不得运行**；客户端可区分失败类别。
- 对“同版本同摘要重传”“同版本不同内容”“降级/重放”“卸载后重新安装旧版本”“主固件 OTA 后兼容性下降”的**本地 v1 语义**按 §3.1/§4.1 决定；这些规则只依赖当前可信、可读取的安装记录，**不得**假设已有跨卸载、NVS 擦除或 Host 回退的安全 anti-rollback 计数器。
- v1 满足一个已提交 App 身份的单次执行、V1→V2 升级闭环。不同业务 App 通过管理员明确卸载旧身份后重新安装，无需刷写主固件；多身份同时安装、批量调度/并发执行不在首版范围。

### 3.1 身份、版本与重试的 v1 预期行为（A 候选语义）

**稳定身份与可追溯性**。安装单元由经设备验证的发行者密钥身份、`app_id`、`app_version` 和已签名包摘要共同标识。包中声明的 `publisher_id` 必须与设备端可信发行者映射一致；仅在名字相同而签名密钥来源不同的情况下不认为是同一个 App。针对同一已安装 App，`publisher_key_sha256` 是必须记录并在安装/执行时与**当前** Host 信任映射重新核对的信任身份维度；不允许未经明确迁移协议的发行者或签名密钥变更、同名身份接管。

**版本规则**。首版建议使用无预发布/构建元信息的 `major.minor.patch` 三段非负整数版本（例如 hello-app `1.0.0 → 2.0.0`），按三段数字顺序比较，不以字典序比较。§2.3 已建议每段为 `u16-le`，范围 `0..65535`，因此无负数或第四段；该编码仍要随 P2 文档整体审查冻结。相同 App 身份的版本增加视为升级；小于当前已安装版本的包默认拒绝为 `DOWNGRADE_FORBIDDEN`，除非未来另行批准恢复流程。此策略仅约束当前可信安装状态：**已按授权完成卸载后**，不保留跨卸载的最高历史版本门槛；重新安装较旧但仍由**当前可信公钥**签名、结构和兼容性均有效的包，可作为**全新安装**按正常管理授权处理，不能无声恢复先前的运行许可。它不是允许覆盖仍已安装的新版，也**不是**安全防回滚、防 Host/信任根回退或历史密钥恢复保证。

**幂等和内容冲突**。同 App 身份、同版本且已验证包摘要相同的重复安装，返回“已安装、未改变”的可核对结果；同身份同版本但摘要不同的包拒绝为 `VERSION_CONTENT_CONFLICT`，不得静默覆盖。另一个发行者同名 App 不得当作升级；**v1 最小支持范围只允许同一时刻一个已提交的 App 逻辑身份（含可查询但 `unavailable` 的旧身份），而非多 App 同时驻留/管理**。已存在其它 `publisher_key_sha256 + publisher_id + app_id` 身份时，新包可在管理员授权下进行独立上传/有界验证，但不得自动接管、删除或覆盖原记录；安装提交返回 `APP_IDENTITY_CONFLICT`，旧状态和数据保持不变。要切换为不同业务 App，管理员须先明确卸载旧身份，再安装经当前 Host 独立验证的目标包；这两次独立操作之间不承诺跨身份原子切换或旧 App 可运行，但**不需要**重新编译/刷写 Host 或基础 Web。若旧记录/共享卷不可判定，优先 `STORAGE_STATE_UNKNOWN` 而非推测已卸载；若正在执行，卸载先以 `BUSY` 拒绝。成功更换后应报告当前身份、活跃版本和包摘要，失败不能虚报新版本已生效。

**重启后的身份**。已提交的可信安装身份应当在重启后仍可被查询；其运行态重置为 `idle`，不会自动执行。若读到无效安装记录或已失效/不兼容的包，或当前 Host 的发行方公钥已改变，应在记录完整时保留可查询身份并标为 `unavailable`、拒绝执行；记录不可读时返回不可确定的存储状态，不能把未知或损坏持久数据当作可信可执行包。每次手动执行均须再次经过当前 Host 的可信钥/签名/ABI/资源/版本可用性检查，而非只信任历史 `installed` 标记。实现所需的持久事务和安全恢复机制仍受 #27 与 P4 验收约束。

### 3.2 逻辑安装/执行状态（A 候选语义）

安装身份至少可观测 `not_installed`、`installed`、`unavailable`（有**可验证的既有安装身份记录**，但包完整性、兼容性或**当前** Host 信任检查不可通过）。**记录或共享卷不可读取/状态不可判定时，不属于上述三个安装状态**：操作返回 `STORAGE_STATE_UNKNOWN` 错误，并拒绝安装、覆盖、卸载和执行，保留介质供非破坏性恢复。只有可靠证明不存在已提交记录时才能返回 `not_installed`；不得把损坏记录猜成未安装，也不得将不可判定状态写成新的持久 App 生命周期状态。上传中、签名检查中、提交中的进度可以呈现为操作状态，**不得**将 `upload_complete` 或 `verified` 混同 `installed`；失败操作保留原已提交版本，除非安装事务真实无法满足该一致性目标，届时必须停在 P2 设计阻塞。

运行状态以 `idle` / `running` / `last_result` 表达可观察行为，`last_result` 包括成功/可恢复错误和有证据的返回码，不虚构强制停止、故障隔离或崩溃后进程状态。即使 App 已安装，也只有管理员明确发起的运行请求可触发入口；设备启动不自动恢复 `running`。

已知正运行时，第二次运行及更新/卸载应返回 `BUSY`，不做并发写入或强行终止。设备不可确认运行状态或重启后记录不可信时，一律禁止盲目执行并报告 `RUNTIME_UNAVAILABLE` 或具体故障。这些是外部语义目标，不预先规定锁、状态表或后端 HOW。

### 3.3 固件/板型兼容与版本记录（A 候选语义）

- **兼容性由当前 Host 判定，而非只看包声明**：每次安装/运行前必须对比包的目标设备、硬件配置、实际可用内存、已部署 Host ABI、声明能力及原生镜像固定头；对任何未经支持的组合拒绝，不能自动降级校验或替 App 猜测“应该能跑”。实验 Host 仅在 64MiB PSRAM 配置验证；32MiB 无兼容性证据，默认拒绝。
- **Host/设备升级并不自动升级 App**：变更主固件/Host 后，已安装身份可查询，但未经重新验证兼容及信任就不得执行；若失配呈现 `unavailable`（保留已知身份和失败原因），不得默默删除用户已安装记录、强制执行旧 ABI 或自动更换 App。恢复执行需重新获得通过验证的兼容包/Host，且该过程须有独立授权，不属于 App 版本替换本身。
- **卸载的幂等语义**：已卸载身份再次请求卸载，应返回可识别的“已未安装/无变更”结果，不把不存在的镜像临时重建或意外删除其他文件。若升级目标已被损坏/失信标记，只有管理员在可追溯的受控路径下重新安装完整可信包才可使它重新 `installed`；具体同身份更换/降级规则仍适用。
- **版本安全边界**：版本号大小不能替代信任校验；拒绝旧版本是当前可读安装记录上的本地产品规则，不宣称有防篡改单调计数器。删除本地记录、恢复备份或切换 Host 之后仍拒绝历史合法签名包，属于需要独立证明的安全反回滚能力，v1 不作此承诺。跨密钥发行者身份迁移、权限扩展和自动迁移现有数据均不在首版隐式处理范围。



## 4. 可信安装与 Web 权限（已确认边界 + A 候选语义）

1. 接收/上传 API 和安装、激活、执行、更新、卸载 API 必须经过适当身份认证和管理员授权；文件能上传到存储**不**表示文件能执行。
2. 设备必须使用受保护的、独立于上传内容的信任锚验证发行方。Web 不能仅凭包自带公钥把未知发行方升级为可信方；验签失败 fail closed。
3. §4.1 已给出 **v1 信任变更规则**：可信 Host 单钥、更换须独立授权的可验证 Host 更新，无在线即时撤销/双钥过渡、不能自动终止运行中原生 App；新 Host 生效后旧已安装包可查但不得再手动执行。**未证实**的是设备受保护信任根、可信 Host 更新、ROM/OTA 可信启动及设备端执行路径，仍需 #29/生产验收，不能把 v1 策略写成已有硬件能力。
4. 设备管理 API 不向 App 入口**显式传递**管理员 Web 会话凭证；但是当前原生 App 运行在特权内存环境，尚无已证明的内存/权限隔离，**不能承诺 App 无法读取或修改主系统内存及凭证**，也不能将该 API 约定解释为沙箱保证。可信 App 的发布管理、安全审查和故障风险控制仍属首版安全边界。

### 4.1 可信发行者与设备信任锚（A 优先方案，待可实施性验证）

**首版候选选择：单一受控发行方 + 实验 Host 固件随版内置的验证公钥/标识。** `.neapp` 是独立签名的外层封装；旧的 32B Host 镜像头及原生 payload 维持 pinned ABI，设备以从已授权 Host 固件取得、**不来自上传包或可任意写入的 LittleFS/NVS** 的预配置验证密钥判定发行方。发布密钥私钥只在离线可信打包/发布端持有；开发测试密钥不得作为生产信任根。App 身份中的 `publisher_id` 需由该可信公钥映射验证，包自称身份无权决定信任。

**关键前提**：这只建立“相对于已可信部署的 Host”的 App 来源核验，**不是**硬件级安全启动、Host 自身防篡改或管理员凭据安全的证明。#27 已记录当前 OTA 验签缺失、裸 Flash 写路径、管理密码处理薄弱；因此不能以“公钥编译进固件”宣称攻击者无法替换 Host 或信任根。若 P4 的实际发布/演示前提不能证明 Host/管理面在所采用的威胁模型下可信，必须缩窄为受控开发验证并明确阻止生产发布。

**密钥撤销/轮换的 v1 边界（A 选择，尚待实施验收）**：v1 的一个可信 Host 版本只允许**一个受控 `publisher_id → SPKI DER/P-256 公钥` 映射**；不允许通过 `.neapp`、Web、普通 NVS/LittleFS 文件写入增加、更改或删除受信密钥，不提供在线即时吊销、双钥过渡或自动重签。需要停用发行者密钥时，**先由单独授权并经核验的 Host/信任策略更新**使新映射实际生效；仅从**新 Host 生效后的下一次安装或手动执行请求起**按当前唯一可信映射拒绝旧钥包。没有可信 Host 更新事实时，不得宣称远程吊销已经完成；对**已经在运行**的特权原生 App 也不承诺即时强制终止。Host 自身 OTA/启动可信性仍未证明，生产撤销保证不得因此推定。

**Host 换钥后已安装 App 的最低可观察结果**：原受信钥指纹不再匹配时，保留可读取且结构完整的既有安装身份/版本/摘要记录，标记为 `unavailable`、拒绝再次手动执行；记录本身不可读时报告存储/状态未知，不能伪造已安装或已卸载。**同名发行者、同 App ID 的新公钥不是旧身份的自动继承者**：安装身份需同时关联已验签的 `publisher_id`、`app_id` 和 `publisher_key_sha256`；不能因名字相同自动替换旧记录、提升权限、沿用旧包的版本次序或进行静默重签。v1 不提供跨钥迁移；如果存在被旧钥占用的同名安装条目，必须先按普通**明确授权、且非破坏性的卸载**完成清理，再按当前可信 Host 映射安装新钥包，不能绕过卸载保留旧身份的可信状态。即使新 Host 能识别新钥，若 #36 管理员准入或 #37 数据保护不满足，仍不允许安装/执行。这是可观察语义，**不是**允许普通 App 包更新 Host。

**密钥/版本恢复跨端验收矩阵（需求，不是已执行 PASS）**：

| 输入与状态 | v1 必须能观察到的结果 |
| --- | --- |
| 包已通过结构检验，但签名所指 `publisher_key_sha256` 与**当前 Host** 唯一受信 SPKI 不符 | `PUBLISHER_UNTRUSTED`，禁止安装和启动；不能改用包附带或历史存储中的旧键自授信 |
| Host 通过独立验证的更新更换信任根，旧包及可读的完整旧安装记录仍在 | 旧条目 `unavailable`、可查但不可再次手动运行；不会删除、重签、自动迁移 |
| 旧条目占用同名 `publisher_id/app_id`，收到新可信钥签名的同名包 | 不自动覆盖旧条目或当作升级；须先按**管理员授权卸载**安全清理，再按新的信任身份安装；卸载故障则保留不可执行状态 |
| 已可信安装 v2，直接上传同身份同钥的 v1 | `DOWNGRADE_FORBIDDEN`，v2 不变 |
| 已正式卸载 v2，当前 Host 仍信任签署 v1 的密钥，重新上传完整合法 v1 | 在结构/签名/目标/管理权限重新核验后允许作为**新安装**，不暗示全局防回滚或自动执行 |
| Host 更新/重启后存储记录不可读、版本来源不明 | 返回明确的存储不可判定错误并拒绝执行，**不能**从文件残留猜测 `installed`、`not_installed` 或安全的最高版本 |

主机端可以为这些行为准备独立负例；后续 #29/#30 的设备准入和事务实现必须分别提供证据。当前没有成功 Host 换钥的目标固件测试、旧包迁移实测或可信防回滚机制；表格只定义该版本计划验收的 WHAT。

**安全反例与最小性自审**：备选“只要 `publisher_id` 相同就自动接管”会让更换密钥造成未经授权的跨信任边界升级，故 v1 拒绝；备选“双钥兼容窗口/在线撤销”需要新增信任策略与运行机制而缺乏设备证据，不适合 v1。最关键、尚未验证的前提是 Host 自身能按受控路径安全更新；如证据否定此条件，只能将可信签名能力定位为**隔离实验 Host 相对信任校验**，不得宣传为生产级撤销或供应链防护。

**两阶段证明，避免循环依赖**：冻结前 A 必须确认算法与签名原文无歧义、源码配置支持的 P-256/DER/SPKI 候选有离线证据、公钥不来自上传包、版号/身份/设备/ABI/资源的条件式拒绝可完整陈述。真实 STM32 Host 目标链接、设备 PKA 行为、性能/占用与信任锚在被替换 Host 下的安全性**仍未被证明**，不得写成事实；它们应明确保留为 P4 #29 的受控实施/验收及生产发布门槛。管理员凭据泄漏另由 #36 修复，不能凭签名策略替代认证。若后续目标链接证据否定 P-256 可行性，必须由 A 重新审议 v1，而非由 B 擅自降级签名。

### 4.2 受信代码的权限与发布约束（A 候选语义）

可信签名只表明包来自 A 已认可的发行方，**不**降低原生 App 对系统内存/外设的权限。已验证 App 依然属于被信任的特权代码；能力声明在未增加强制执行机制前仅可作为兼容性/风险元数据，不能当作内存或数据访问控制。V1 只用实验 Host 公开的 `log`、`tick_ms` 支撑 hello-app，任何扩大 Host API 或允许其他发行方是另一次显式协议/风险评估。

### 4.3 设备可信准入的安全前提与拒绝规则（A 候选决策；非设备测试）

**证据基线**：[ne301 #27 已合并调查](https://github.com/harryhua-ai/ne301/blob/b00584d598628ebeefdd95bbb6c43ffd4477f412/Docs/design/app-install-feasibility.md) 与 [#32 待完成的整改 Candidate](https://github.com/harryhua-ai/ne301/blob/8a8bd77acb8a3f4b19dda14df042632cf7fb01ba/Docs/design/app-signing-feasibility.md)。现有 mbedTLS 配置支持 SHA-256/ECDSA P-256、目标 PKA ALT 路径有源码依据，主机侧同源软件签名测试通过；但 **NE301 实机没有已接入的 App 包验签入口、没有目标板验签/链接/资源实测、没有证明受保护的 Host 信任根**。现有 OTA 主固件升级未实施可信签名校验，FSBL→App 缺少签名校验，管理员密码处理存在明文日志/弱存储风险，ROM authentic boot 的实际配置未知。三者不得以“固件编入一把公钥”替代。

在 User 已确认的“**受控发行者签名 + 管理员手动执行**”范围内，A 对**新 App 安装与执行**定义以下 fail-closed 语义（不等于承诺现有固件已经实现）：

| 风险或事件 | 对外必须满足的行为 | 必须承认的限制 |
| --- | --- | --- |
| 发布者未知、设备侧受信公钥缺失/不匹配、签名或任一受覆盖字段无效 | 禁止首次安装/激活；已有条目可以保留供查询，但不得通过新的执行准入 | 包中 `publisher_id` / `publisher_key_sha256` 只能被设备独立信任配置核对，不能把包自带指纹当新信任根 |
| 重启/Host 更换导致旧 App 的签名身份、ABI、板型、资源不可再证明 | 保留已知、完整、可信的持久记录；将不兼容 App 标为 `unavailable`，并拒绝新的手动执行 | 不能把失信状态静默删除后假装 `not_installed`；若**记录本身不可读取**，应报存储错误/状态未知，不能伪造原状态 |
| 发行方密钥需要紧急停止使用 | 停止新包发布；**设备侧只有实际部署、验证过的撤销/新 Host 策略后**才能声明旧包被禁止执行 | 首版没有已证实的在线撤销服务或“马上停止正在运行的特权 App”能力；不得把管理界面标记等同于技术撤销 |
| 设备管理密码可能泄露、已有不验签 OTA 可替换固件 | 产品可触达的可信安装/执行须暂停，直到有独立核验的管理入口与 Host 更新渠道保护或等效受控隔离 | 固件编入 App 验签公钥可以是纵深防御，**不是**生产可信启动/防 Host 替换的证明 |
| 调试 UART 裸镜像装载/普通上传/固件更新仍可能绕过 App 准入 | 任何被称为“可信安装”的实验流程必须确保这些入口不会让未验签内容进入其**产品 App 执行路径**；保留的诊断入口必须经受控隔离、不对一般用户开放 | 不能声称签名机制约束所有系统可执行代码；原生 App 仍以 Host 特权运行，无沙箱 |

**信任根生命周期的最小范围**：v1 仅允许**一位受控发行者及一把 Host 固定公钥**，不允许用户 Web 上传/切换信任根，也不启用云端密钥分发。计划更换或撤销公钥时，不重写旧包来“自动迁移”；先通过另行受权且可验证的 Host/信任策略更新，再逐个重新判断历史安装条目的准入。当前 OTA/ROM 信任事实不足，不得称此流程已具备安全更新保证。若未来需要在**不更新固件**的情况下秒级撤销，这是新能力与风险决策，不在首版实现授权内。

**源码复核对 P2 的额外影响（#36/#37 Prepared）**：当前 `web_server.c` 的认证路径直接按请求解析管理员口令，还记录 `Authorization` 原文及口令；`api_auth_module.c` 的 `/login` 返回成功但不创建真实会话，密码更新在保存失败时也可能返回成功。不能以旧会话接口或单纯删日志作为可信管理员门槛的实现证据。另 `storage.c` 对 NVS factory/user 初始化失败同样存在擦除+复位逻辑；因此 [#37](https://github.com/harryhua-ai/ne301/issues/37) 先解决 **LittleFS/NVS** 非破坏性启动，再允许 [#36](https://github.com/harryhua-ai/ne301/issues/36) 迁移管理员口令；#29 仍以 #36 完成作为语义前提。任何需要改变旧账号恢复体验、管理协议或开放公网高危入口的实质产品取舍须先经用户确认，不能借准备任务自动授权。

**补充的旧凭据准入语义（#36）**：已有有效管理员凭据应在可核实、无数据丢失的迁移中保留其可用性；旧/新 NVS 密码记录冲突、读取失败或状态未知时 **不得回退已知公开默认口令并授予高危 App 权限**。新介质首次初始化须与旧配置损坏区分；密码改动只有持久存储完成并验证之后才能返回成功，失败不得令 RAM 与重启后的真实凭据不一致。真正可被 Web 消费的认证路径优先于未被使用的会话辅助函数；传输机密性未经验证，不开放生产可触达的高危 App 安装接口。具体强口令散列、迁移策略和部署 HOW 由安全任务提供可复核结果，不在 P2 提前指定算法。

**P4 #29 准入与产品发布的两道不同门槛**：受控实验中可在单独批准的只读/隔离环境验证 mbedTLS PKA、包签名、缺钥/错钥及入口拒绝；**生产可触达**安装还需要真实管理员凭据保护、可验证的 Host 投递可信性与平台安全边界。即使第一道完成，也不得自动宣称第二道已通过；不得以在固件中发现 PKA 驱动就记作设备验签通过。

## 5. 安装、更新与失败恢复（目标语义；#27 已验收调查，不等于机制已证明）

首版对外目标路径：`未安装 → 接收/暂存 → 检查签名/摘要/兼容/资源 → 提交已安装版本 → 管理员手动执行 → 返回或报告故障`。更新必须先完整验证候选包，不能先破坏旧版本再决定其是否可信。

用户可观察的最低一致性规则：

- 接收中断、验签或兼容失败：不得新增可执行的半包，不得改变已安装的有效版本。
- 安装/升级提交异常或重启：恢复后必须是**旧版本或完整新版本**的明确可判定状态，不能把不完整包当作可执行安装；旧版是否需要在成功提交后保留，需根据容量与事务机制定案。
- 空间不足、写入失败和重复请求：返回可解释的失败/结果，不覆盖其他 App 或用户数据；v1 **不另设第二个 App 幂等身份或独立客户端请求键**。已完成校验的同身份/同版本/同 `SHA-256(TBS)` 安装重试结果为 `already_installed/no_change`；上传中断及提交中断仍按 §5.1 旧/完整新版本和 `STORAGE_STATE_UNKNOWN` 的失败结果处理，不得为了“重试成功”跳过管理员授权、签名验真或持久状态检查。
- 卸载：移除该 App 的可执行/管理元信息，不误删其他持久数据；首版无 App 私有存储 API，未来应用数据清除/保留属于新版本协议，不应被臆造。
- 切勿为 App 安装改写 FSBL、APP1/APP2、OTA 信息、基础 Web、AI 分区或任意未明确授权持久区。

### 5.1 安装/升级/卸载的失败结果矩阵（A 候选验收语义；非实测）

| 场景 | 对外允许结果与数据不变量 | 禁止的假成功 |
| --- | --- | --- |
| 从未安装：上传中断或坏包 | 保持 `not_installed`；暂存物不得被执行 | 上传了一部分就显示 `installed` |
| 已安装 V1：上传/验证 V2 失败 | 有效 V1 及其可查询身份不变；V2 不得执行 | 用坏 V2 覆盖已提交 V1 |
| V1→V2 提交中断/掉电 | 重启后可验证地指向**完整 V1 或完整 V2**之一；失败/恢复原因可查询；无不完整可执行版本 | 只剩半包、版本记录与镜像不一致或静默删除原始数据 |
| 无空间/碎片化/存储读写异常 | 在保证旧有效数据/既有其他文件安全的前提下拒绝提交；必要时进入不可执行的受控故障状态 | 因 mount 失败自动格式化整个共享用户卷并报成功 |
| 同身份、同版、同包摘要再次安装 | `already_installed/no_change`，不得产生不必要的版本切换 | 将重试伪装成一个不同的成功新版本 |
| 同身份同版本而包摘要不同 | `VERSION_CONTENT_CONFLICT`，原安装状态不变 | 静默覆盖而无法解释版本来源 |
| 已安装版本高于候选版本 | `DOWNGRADE_FORBIDDEN`，除非未来明确受权的恢复协议 | 用签名正确作为允许降级的理由 |
| 新设备/Host 的目标或 ABI 不匹配 | `TARGET_INCOMPATIBLE` / `ABI_INCOMPATIBLE` / `RESOURCE_LIMIT`；不可执行；先前可用版本不被静默替换 | 忽略 manifest/镜像头冲突 |
| 当前正在运行 | 第二次运行、更新、卸载以 `BUSY` 拒绝；不假设可安全强制终止 | 写入或卸载运行中执行镜像，或假报停止成功 |
| 当前已提交其它 App 身份时尝试安装不同 `publisher_key_sha256 + publisher_id + app_id` | 拒绝提交为 `APP_IDENTITY_CONFLICT`，旧安装身份/数据保持原样；须独立明确卸载后才允许新身份安装 | 把新身份静默作为旧身份的升级、借“切换 App”清理旧数据或无需验证自动接管 |
| 管理员卸载后或重复卸载 | 卸载提交成功后该身份不可执行；重复卸载返回无变更；其他 App/用户数据不变 | 删除了普通文件就断言已撤销所有执行入口 |
| 重启、信任撤销或 Host 不再兼容 | 若旧记录可信可读，保留身份并重新判断 `installed` 或 `unavailable`；**不自动运行** | 自动运行失信/不兼容代码，或隐匿记录丢失 |
| 共享卷/安装记录损坏、读取失败、记录是否存在无法确定 | 返回 `STORAGE_STATE_UNKNOWN` 请求错误，拒绝安装、替换、卸载及执行，保留原始内容供恢复；**不推定任何安装身份状态** | 将读失败显示为 `not_installed` 或把未知文件当合法新版本清理/执行 |

“旧版本或完整新版本”是 **P4 必须证明的产品 AC**，不是 LittleFS rename、文件删除或 #2 离线注入已经提供的事实；如果设备路径无法达到该结果，A 应暂停/重新规划 P4，而非放宽为“通常能成功”。严格保留现有 `/captures`、日志、配置等共享用户数据，备份丢失也不能被伪装成成功回退。

**已核实的风险与尚未完成的证明**：#27 的 [受审调查报告](https://github.com/harryhua-ai/ne301/blob/b00584d598628ebeefdd95bbb6c43ffd4477f412/Docs/design/app-install-feasibility.md) 确认当前 LittleFS mount 失败时有静默格式化路径；#2 的 4KiB 小段 SWD 写/编程器 64KiB 擦除重叠事故曾触发数据丢失，96MiB 全卷恢复后经内容清单验证，但**不能**据此推断固件运行时的掉电行为。旧 counting APP1 有备份但实际恢复未测试，APP2/OTA 切槽仍是未证备选，关键备份只在 `/tmp` 单副本。P4 只能把经独立证明、设备现存数据保护边界内的文件区域作为 App 候选存储；不得复用 APP1/APP2 或单槽 WEB/AI/FSBL。安装事务必须保留旧有效版本直至新版本可确认提交，且 mount/写入异常不能静默抹掉用户其他数据。**实现此目标需要重新设计或拦截现有危险恢复路径并经专门验证，现有文件 API 不提供产品安装事务证明**。在批准任何板卡写入前，必须有可持久保存、完整核对的独立备份与真实可行的回退路径；否则只允许静态/离线验证，不得冒称 AC 通过。

### 5.2 文件卷异常和安装记录恢复（A 外部语义；不得误认已实现）

已验收的 [#27 §1.3](https://github.com/harryhua-ai/ne301/blob/b00584d598628ebeefdd95bbb6c43ffd4477f412/Docs/design/app-install-feasibility.md) 表明，当前 `lfs_mount` 失败后会调用 `lfs_format` 并重挂载；更早的 hello-app 真机试验曾遭遇共享卷数据丢失，后来从备份恢复。**在此原路径不变的情况下，不能声称“App 安装失败不会格式化现有 LittleFS”**。单纯在安装 API 内返回错误，也不能防止启动时更早的挂载路径先清空用户数据。

首版 App 安装/恢复对外至少必须满足：

- **启动/挂载失败**：进入保护现存数据的故障路径，不得为使 App 安装继续而自动初始化、擦除或重新格式化包含 `/captures`、日志、配置及历史文件的共享卷；无可信卷就禁止安装、更新及执行。具体系统其他功能如何退化须与现有平台兼容性一起审查，不能未经实现承诺整机可用。
- **元数据不可读或不一致**：返回明确的存储/安装状态不可判定结果，禁止执行；不得把“读取失败”报成 `not_installed`，也不得凭无签名、无原子证明的孤立文件“恢复”出已安装版本。已有完整且受信任的版本若无法核对，保留原始存储以待非破坏性恢复。
- **升级提交**：必须先完整暂存并验证新包，保留旧版直到存在可恢复的提交决定；中断后只允许完整旧版或完整新版，无法判定时拒绝执行并提供可审计故障。LittleFS `rename` 的存在**不是**跨断电原子事务的证明。
- **卸载/空间不足**：仅修改所选 App 的受控条目和文件；空间不足或卸载中断不清空共享目录、其它 App/配置/日志；如果存储后端不能承诺这些不变量，暂停 P4 #30 READY 而非降低验收标准。
- **写板验证前**：需要现有设备身份、分区与用户文件清单、可长期保存并逐项校验的备份、具备实际恢复能力的回退方案和单独设备写入许可。仅凭此前 96MiB 整卷恢复及 `/tmp` 单份备份，不足以授权新的危险注入。

**源代码进一步核实的存储危险入口（#37）**：除 `lfs_mount→lfs_format`、NVS factory/user 初始化失败擦区重启外，`json_config_mgr_init` 在 NVS 加载失败后可能回退默认配置并写回，可能在未删除整个分区时仍覆盖旧信息。当前管理员 Web 存在显式 `POST /device/storage/format`（`require_auth`）；其调用 `void storage_format()` 后直接形成成功响应，不可证明格式化真的成功。v1 要区分：①可信旧介质继续使用；②独立证明空白且经受控授权才初始化；③未知/损坏/读失败时保留原样、禁止 App 写入和执行，不自动擦除、重置管理员口令或默认写回。保留有意的管理操作与“出错就自动抹盘”不同；现行认证尚不安全，既有显式格式化入口不能仅凭 `require_auth` 被当作安全恢复。格式化具体交互/权限的 User-owned 变更待另行确认，不由 P2 臆造 UI。

**工程实现仍归后续 B 的 HOW**：本节只冻结待验证的可观察安全要求，不指定“双份日志”“双槽 Flash”或另造任务状态系统。P2 草案当前没有证明写入路径、掉电测试或目标固件已修复，不能提前将 #30 AC3/AC4 判 PASS。

## 6. 执行生命周期（已确认边界 + A 候选语义）

- 唯一首版入口是管理员显式发起的一次性执行，Host 校验当前已安装镜像的完整性/兼容性并以既定 ABI 调用；执行结束记录结果码/可取得的日志。**重启后默认不自动运行**。
- V1/V2 的执行必须证明两个独立产物在同一 Host 上替换运行，且主固件/基础 Web 前后不变。实验 #2 已证明的只是 UART 命令 + LittleFS 注入实验路径，不能代替 Web 安装验证。
- 不能承诺原生代码的抢占式安全停止、运行超时杀死、内存隔离或崩溃后主系统存活；这些属于尚无证据的能力。异常后的状态恢复、执行中更新/卸载的禁止/等待规则须在设备边界清楚后明确，不得默认并发安全。

## 7. 面向 P3/P4/P5 的错误与证据接口（A 候选语义）

对外至少区分 `AUTH_REQUIRED`、`FORBIDDEN`、`BAD_PACKAGE`、`SIGNATURE_INVALID`、`PUBLISHER_UNTRUSTED`、`TARGET_INCOMPATIBLE`、`ABI_INCOMPATIBLE`、`RESOURCE_LIMIT`、`STORAGE_FULL`、`STORAGE_STATE_UNKNOWN`、`COMMIT_FAILED`、`RUNTIME_UNAVAILABLE`、`BUSY`、`APP_IDENTITY_CONFLICT`、`DOWNGRADE_FORBIDDEN`、`VERSION_CONTENT_CONFLICT`。其中 `STORAGE_STATE_UNKNOWN` **是请求失败类别，不是第四种可持久化的安装状态**；只有无法判定现有卷/已提交安装身份时使用，不把它等同于写提交失败、磁盘满或已知 App 不兼容。权限与验签检查失败不得切换已安装版本或暴露攻击者可利用的密钥/内部错误信息。枚举值/HTTP 映射及记录恢复中状态仍待最终协议冻结；不得把上传成功、签名通过或后台文件已存在误报为安装成功。

### 7.1 请求结果与状态优先级（A 候选语义）

- **认证优先**：未通过管理员授权的上传、查询敏感包信息、安装/升级/卸载和运行请求一律拒绝，不向未授权调用者泄露已安装发行者、公钥细节或包解析细节。管理员授权通过后，仍须独立验证设备信任锚与包签名；有文件读写权限不等于获准执行。
- **验证不是提交**：上传/暂存成功、包结构解析成功、签名通过、兼容检查通过是不同操作结果；只有持久提交被证明成功才能返回 `installed` 与有效身份/版本/摘要；返回结果必须使 Web 可区分“失败但旧版仍有效”“未知/不可信不可运行”“已成功升级”。具体 HTTP 状态码/传输 JSON 字段、原始错误枚举的数值和长度限制待 wire/API 规范冻结。
- **错误至少覆盖**：认证/授权、包结构、签名失效/未知发行者、设备/ABI/资源不兼容、版本冲突/降级、运行忙、存储容量/提交失败和运行不可用。可能有多个错误时不保证客户端看到每一种原因；对外保证返回稳定且不泄露密钥或内部路径的**主分类**，并保留仅管理员可审计的有效版本与必要操作记录。
- **手动运行结果不得混同安装结果**：正常返回的 App 返回码与加载器的系统错误是不同数据；当前实验入口返回值经包装，不能臆造崩溃可恢复的执行结果或长期运行状态。发生设备异常/不可证明运行状态时，管理 API 不得假报成功。

拟冻结的跨仓库验收场景：可信 V1 安装与手动运行；同 Host 下可信 V2 替换；篡改 manifest/payload 或错误签名/不可信发行者拒绝；错误板型/ABI/大小拒绝；普通用户和未认证者拒绝；写入失败/容量不足/断电重启后完整旧/新状态；卸载后无法再运行；主固件与基础 Web 未发生 App 替换写入。这些是协议证据期望，**不代表任何场景已在 P3/P4 实测**。

**v1 校验与错误语义的最小判定顺序（A 候选，不是 HTTP 协议）**：

1. **管理入口先授权**：无有效凭据返回 `AUTH_REQUIRED`；已有身份但权限不足返回 `FORBIDDEN`。禁止在拒绝前把解析过的发行者/镜像/密钥错误暴露给请求者，不得因只是上传文件就授予执行权。
2. **有界结构解析 → 可信发行者 → 密码学验签**：magic、包长、manifest 160B 唯一编码、DER 结构与尾段完整消费失败属 `BAD_PACKAGE`；不在 Host 自身信任映射的发行者/公钥摘要属 `PUBLISHER_UNTRUSTED`；在可信键上对 **原样 TBS** 验签失败属 `SIGNATURE_INVALID`。不能把包自带的键用作信任来源。为了防止长度溢出，初步有界结构检查须先于密码学操作；不规定对攻击者公开的逐字段错误细节。
3. **签名有效仍需策略校验**：已签名文件自身的 native SHA-256、CRC 或头部/manifest 不一致仍须拒绝为无效包；目标型号/硬件不符报 `TARGET_INCOMPATIBLE`，Host API/ABI 不符报 `ABI_INCOMPATIBLE`，执行/存储资源不足归 `RESOURCE_LIMIT` / `STORAGE_FULL`（按具体已能证实的原因）。禁止将“签名通过”直接写成可执行的 `installed` 状态。
4. **持久版本和运行状态由设备判定**：只有能核实已提交身份或确实未安装时才可比较身份占用（跨身份安装报 `APP_IDENTITY_CONFLICT`）、版本、幂等、降级和内容冲突；共享卷/安装记录无法核对时返回 `STORAGE_STATE_UNKNOWN`，不得尝试依靠残留文件恢复身份，也不得擅自卸载清理。已知运行中发生并发运行/更新/卸载返回 `BUSY`；若是执行状态本身无法证明安全则报告 `RUNTIME_UNAVAILABLE`，**不与存储状态未知混同**。实际提交失败报告 `COMMIT_FAILED`，不能以该错误掩盖更早就无法核实的安装身份；只有已证实持久提交的版本才可变成 `installed`。
5. **多种故障同时成立时**，对外必须优先保证：未授权不泄露信息、畸形长度不进入越界解析、无签名/无信任不进入执行、未提交不标记成功。除以上先决关系外不承诺每个字段级错误码在复合坏包上的固定优先级；P5 的 HTTP 状态整数及 JSON 映射另按**这份既有错误主分类**设计，不另建一套包解析协议。

**状态未知的独立验收负例（仍非已执行测试）**：①完整可信旧记录与旧包存在但信任根被换掉，应查询为 `unavailable`；②损坏或无法读取原有记录，查询与安装/卸载/执行均返回 `STORAGE_STATE_UNKNOWN`、数据不被自动改写；③已可信证明从未安装才是 `not_installed`；④记录可读且新包提交写入失败才报告 `COMMIT_FAILED`，旧有效版本保持不变。P3 可做离线错误模型/文档核对，但共享卷与断电恢复拒绝证据必须由后续 #30/#31 在获得独立授权后提供，不能把表格当成设备 PASS。

**该段可观察行为不是实现接口方案**：B 可以选用已有 Host/mbedTLS/HTTP 的不同检查函数，只要最终保持相同安全语义及共享向量的预期。P2 冻结前须完成 A 对单错误类别的正负样本自审，P3/#29 各自实施后须提供独立拒绝证据。主机向量的 `SIGNATURE_INVALID` 示例只代表该例经过了结构检查，不表示任意篡改都必须绕过 `BAD_PACKAGE` 先到验签步骤。

### 7.3 顺序与证据分层（A 的关键路径决定；不降低 AC）

P3 #6 的机械依赖为 P2 #4，P4 #29 依赖 #27 / #36 且另需**已合并的 P2 版本规范**。故**禁止**要求 P3 的产物或 P4 的设备验签 PASS 作为 P2 规范冻结的先决条件；那将形成 `P2 → P3/P4 → P2` 的循环依赖。可实施的顺序及不可替代的证据如下：

| 阶段 | A/B 的完成边界 | 尚不得声称 |
| --- | --- | --- |
| **P2 #4 A 决策与定稿** | A 在单一 PR 审查后固定容器/manifest、TBS、信任锚映射、候选设备约束、错误/失败/运行语义、带完整 HEX/哈希的**主机离线黄金及负例**；真实板型/容量/PKA/OTA 的未证能力写为明确拒绝条件或后续受控 AC，不能把未知冒充肯定 | 不宣称 P3 打包器、STM32 PKA、设备安装/掉电或生产可信启动已通过 |
| **P3 #6 离线工具验收** | 消费已合并的 P2 规则与固定测试字节，重现两版原生 App、打包并独立验证正负向量；不更改 NE301 工作树 | 不宣称设备可执行/安装或密钥具备生产防护 |
| **P4 #29 验签与管理准入验收** | 在 #27、#36 canonical 依赖完成及 P2 冻结后，B 独立证明 MCU 目标链接/PKA/信任公钥、资源/板型与管理员拒绝；仅获另行设备授权才可碰板 | 不凭主机测试/代码存在就宣称真实设备验签/权限安全 |
| **P4 #30/#31 事务与单次运行验收** | 复用完成的 #37 共享数据保护和 #29 准入，分别证明完整提交/故障恢复与管理员单次运行；不重复开发存储、安全登录或 Host | 不凭正常路径成功就宣称断电原子性、数据完好或原生隔离 |
| **产品 Web/发布验收** | 端到端 V1→V2、权限/失败状态、真实备份回退、可信 Host 更新与生产安全另行核验 | 不从 P2 规范合并或 `ready` 推导可对外发布 |

**拒绝路径**：如果 P3/P4 真实实验证明冻结的 P2 字节格式、所选 P-256 验签、资源边界或错误承诺不可实现，不允许局部私改；B 提交证据，A 重开唯一 P2 规范的受控版本修订并重新判断依赖/风险。在这之前，对不兼容或无法证实的设备 fail closed。这样既不预先豁免任何设备验收，也不让尚未获 READY 的实现阻塞设计定稿。
