## 1. 产品边界（已确认）

首个 Web MVP 只允许经过认证且具管理员权限的使用者，从 NE301 Web 管理**可信发行方签名且验证通过**的独立 App；至少支持 hello-app V1 → V2 的安装/替换、手动执行一次、更新、卸载、状态和失败原因。更换业务 App 不能重新链接、重编或刷写主固件及基础 Web。首次经过独立授权部署通用 Host 不等于更换 App 的一部分。

首版**不**提供开放第三方不可信原生代码、普通用户自行安装、App Store、后台常驻或多 App 调度、开机自动运行、任意代码强制停止或生产级沙箱隔离。签名认证不能证明签名代码无漏洞；既有实验 Host 未证明 App 出错不会拖垮主系统。

`ne301` 独立实现平台 Host、设备验签、安装及管理 API，**不得**静态引用 `ne30x-app` 业务源码；`ne30x-app` 独立构建 App 与离线打包/验证，不得复制 NE301 私有平台实现。Host ABI 的唯一权威仍在 NE301。

## 2. 包的逻辑契约（A 候选语义；字节格式尚未定稿）

`.neapp` 是首版候选文件后缀。单一包包含**一份明确版本化 manifest、一份不透明的 NE301 原生 App 镜像 payload、可验证的发行方签名信息**；不得用裸 `.bin` 或仅 CRC/SHA 通过的文件冒充已受信任的安装包。

manifest 至少有以下逻辑字段；名称、字节编码、排序、是否使用整数等均须在最终 wire-spec 中冻结：

| 逻辑字段 | v1 要求/约束 |
| --- | --- |
| `package_format_version` | 标识包容器的版本，未知重大版本拒绝 |
| `publisher_id`、`app_id`、`app_version` | 身份与版本可比较、可追溯；`publisher_id` 必须绑定到验签成功的可信身份，不能信任未经认证的自称 |
| `target_device`、`hardware_profile` | 显式声明目标 NE301 板型/资源条件；实验基线只验证 64 MiB PSRAM，32 MiB 不能默认兼容 |
| `required_host_abi` | 明示所需 ABI，现有实验基线是 `0x00010000`；不得依赖 App 端复制私有头 |
| `image_descriptor` | payload 长度、摘要与入口/镜像头一致性；必须按 NE301 权威镜像头及当前 Host 兼容约束交叉校验 |
| `required_capabilities`、`resource_bounds` | 可审计的能力要求和最大空间/运行预算；当前 Host 仅开放 `log`、`tick_ms`，未声明能力不得静默升级 |
| `signature_identity`、`signature` | 标明可由设备预置信任体系识别的发行方验证密钥/算法标识；签名覆盖所有安全相关元数据并绑定 payload 完整字节 |

**完整性与来源认证分离**：payload 摘要/镜像头 CRC 只检出损坏，不能证明可信来源。包验证须防止包内字段混淆、追加未验证 payload、manifest 与镜像头冲突、同一字段多义编码或签名未覆盖兼容字段。具体容器序列化、签名原文构造、算法、密钥长度、测试向量均为 **待证据/阻塞**；因此这一节不可直接用于实现兼容打包器/验签器。

## 3. 身份、版本和互操作（A 候选语义）

- 以发行者身份 + App ID 确定 App 逻辑身份；同身份的新版本才是升级，换发行者不能静默接管旧 ID。
- 成功安装应回报已验证的发行者、App ID、版本、包/镜像摘要及 ABI/板型兼容结果，供 Web 和运维核对。上传或离线打包成功均**不**代表已安装或获执行权限。
- 未知包版本、错误目标板/ABI、签名不可识别/失效、摘要不符、资源限制不满足时，**拒绝安装且不得运行**；客户端可区分失败类别。
- 对“同版本同摘要重传”“同版本不同内容”“降级/重放”“卸载后重新安装旧版本”“主固件 OTA 后兼容性下降”的最终策略必须与可信密钥及可用持久存储共同定案，当前**不得**假设已有 anti-rollback 安全计数器。
- v1 至少满足一个 App 身份的单次执行、V1→V2 升级闭环；批量调度/并发执行不在首版范围。

### 3.1 身份、版本与重试的 v1 预期行为（A 候选语义）

**稳定身份与可追溯性**。安装单元由经设备验证的发行者密钥身份、`app_id`、`app_version` 和已签名包摘要共同标识。包中声明的 `publisher_id` 必须与设备端可信发行者映射一致；仅在名字相同而签名密钥来源不同的情况下不认为是同一个 App。针对同一已安装 App，不允许未经明确迁移协议的发行者变更或身份接管。

**版本规则**。首版建议使用无预发布/构建元信息的 `major.minor.patch` 三段非负整数版本（例如 hello-app `1.0.0 → 2.0.0`），按三段数字顺序比较，不以字典序比较。其最大值、字段宽度和 manifest 的编码尚待 wire-spec 冻结。相同 App 身份的版本增加视为升级；小于当前已安装版本的包默认拒绝为 `DOWNGRADE_FORBIDDEN`，除非未来另行批准恢复流程。此策略仅约束当前可信安装状态，**不承诺卸载后仍具安全反回滚计数器或防重放保证**。

**幂等和内容冲突**。同 App 身份、同版本且已验证包摘要相同的重复安装，返回“已安装、未改变”的可核对结果；同身份同版本但摘要不同的包拒绝为 `VERSION_CONTENT_CONFLICT`，不得静默覆盖。另一个发行者同名 App 不得当作升级；允许多个独立 App 身份是否与首版 RAM/存储条件兼容待证据确定，但单次仅执行一个 App。成功更换后应报告活跃版本和包摘要，失败不应虚报新版本已生效。

**重启后的身份**。已提交的可信安装身份应当在重启后仍可被查询；其运行态重置为 `idle`，不会自动执行。若读到无效安装记录或已失效/不兼容的包，应标记不可执行并报告原因，不能把未知或损坏持久数据当作可信可执行包。实现所需的持久事务和安全恢复机制仍受 #27 与 P4 验收约束。

### 3.2 逻辑安装/执行状态（A 候选语义）

安装身份至少可观测 `not_installed`、`installed`、`unavailable`（曾安装但完整性、兼容性或信任检查不可通过）。上传中、签名检查中、提交中的进度可以呈现为操作状态，**不得**将 `upload_complete` 或 `verified` 混同 `installed`；失败操作保留原已提交版本，除非安装事务真实无法满足该一致性目标，届时必须停在 P2 设计阻塞。

运行状态以 `idle` / `running` / `last_result` 表达可观察行为，`last_result` 包括成功/可恢复错误和有证据的返回码，不虚构强制停止、故障隔离或崩溃后进程状态。即使 App 已安装，也只有管理员明确发起的运行请求可触发入口；设备启动不自动恢复 `running`。

已知正运行时，第二次运行及更新/卸载应返回 `BUSY`，不做并发写入或强行终止。设备不可确认运行状态或重启后记录不可信时，一律禁止盲目执行并报告 `RUNTIME_UNAVAILABLE` 或具体故障。这些是外部语义目标，不预先规定锁、状态表或后端 HOW。

### 3.3 固件/板型兼容与版本记录（A 候选语义）

- **兼容性由当前 Host 判定，而非只看包声明**：每次安装/运行前必须对比包的目标设备、硬件配置、实际可用内存、已部署 Host ABI、声明能力及原生镜像固定头；对任何未经支持的组合拒绝，不能自动降级校验或替 App 猜测“应该能跑”。实验 Host 仅在 64MiB PSRAM 配置验证；32MiB 无兼容性证据，默认拒绝。
- **Host/设备升级并不自动升级 App**：变更主固件/Host 后，已安装身份可查询，但未经重新验证兼容及信任就不得执行；若失配呈现 `unavailable`（保留已知身份和失败原因），不得默默删除用户已安装记录、强制执行旧 ABI 或自动更换 App。恢复执行需重新获得通过验证的兼容包/Host，且该过程须有独立授权，不属于 App 版本替换本身。
- **卸载的幂等语义**：已卸载身份再次请求卸载，应返回可识别的“已未安装/无变更”结果，不把不存在的镜像临时重建或意外删除其他文件。若升级目标已被损坏/失信标记，只有管理员在可追溯的受控路径下重新安装完整可信包才可使它重新 `installed`；具体同身份更换/降级规则仍适用。
- **版本安全边界**：版本号大小不能替代信任校验；拒绝旧版本是当前可读安装记录上的本地产品规则，不宣称有防篡改单调计数器。删除本地记录、恢复备份或切换 Host 之后仍拒绝历史合法签名包，属于需要独立证明的安全反回滚能力，v1 不作此承诺。跨密钥发行者身份迁移、权限扩展和自动迁移现有数据均不在首版隐式处理范围。



## 4. 可信安装与 Web 权限（已确认边界 + A 候选语义）

1. 接收/上传 API 和安装、激活、执行、更新、卸载 API 必须经过适当身份认证和管理员授权；文件能上传到存储**不**表示文件能执行。
2. 设备必须使用受保护的、独立于上传内容的信任锚验证发行方。Web 不能仅凭包自带公钥把未知发行方升级为可信方；验签失败 fail closed。
3. 对有待激活/正在执行的 App，后续信任撤销和密钥轮换应有明确禁用、可见状态与恢复语义；**信任锚持久化与可保护性、密钥轮换/吊销入口属于 #27 后待定的重要安全决策**。
4. 设备管理 API 不向 App 入口**显式传递**管理员 Web 会话凭证；但是当前原生 App 运行在特权内存环境，尚无已证明的内存/权限隔离，**不能承诺 App 无法读取或修改主系统内存及凭证**，也不能将该 API 约定解释为沙箱保证。可信 App 的发布管理、安全审查和故障风险控制仍属首版安全边界。

### 4.1 可信发行者与设备信任锚（A 优先方案，待可实施性验证）

**首版候选选择：单一受控发行方 + 实验 Host 固件随版内置的验证公钥/标识。** `.neapp` 是独立签名的外层封装；旧的 32B Host 镜像头及原生 payload 维持 pinned ABI，设备以从已授权 Host 固件取得、**不来自上传包或可任意写入的 LittleFS/NVS** 的预配置验证密钥判定发行方。发布密钥私钥只在离线可信打包/发布端持有；开发测试密钥不得作为生产信任根。App 身份中的 `publisher_id` 需由该可信公钥映射验证，包自称身份无权决定信任。

**关键前提**：这只建立“相对于已可信部署的 Host”的 App 来源核验，**不是**硬件级安全启动、Host 自身防篡改或管理员凭据安全的证明。#27 已记录当前 OTA 验签缺失、裸 Flash 写路径、管理密码处理薄弱；因此不能以“公钥编译进固件”宣称攻击者无法替换 Host 或信任根。若 P4 的实际发布/演示前提不能证明 Host/管理面在所采用的威胁模型下可信，必须缩窄为受控开发验证并明确阻止生产发布。

**密钥撤销/轮换的最小语义**：不开放 Web 上传新受信发行者公钥、不默认在线轮换。密钥需要停止使用时，设备必须在新的执行请求前禁止该发行者包运行，并通过**另行授权的 Host/信任策略更新流程**替换或废止信任根；首版方案不能承诺无需固件更新的紧急密钥轮换或撤销。实际“如何安全禁用”及更新前后已安装包状态仍须在 wire spec 与设备准入设计中明确；它不属于普通 App 替换操作，不能借此修改受保护固件。无法建立必要的失效处理时不得声称完整可运营的代码签名生态。

**需要 A 在冻结前证实的条件**：NE301 实验 Host 的真实构建中，所选验签算法/密钥长度/性能/代码体积可用；公钥本身不会被未授权 App 包写入改动；签名所覆盖的包版本/身份/硬件/ABI/资源声明无歧义；现有管理认证泄密路径不会被误当 App 签名认证。这些与完整 wire-format、测试向量及设备身份保护一并列为剩余 P2 决策/验收门槛。

### 4.2 受信代码的权限与发布约束（A 候选语义）

可信签名只表明包来自 A 已认可的发行方，**不**降低原生 App 对系统内存/外设的权限。已验证 App 依然属于被信任的特权代码；能力声明在未增加强制执行机制前仅可作为兼容性/风险元数据，不能当作内存或数据访问控制。V1 只用实验 Host 公开的 `log`、`tick_ms` 支撑 hello-app，任何扩大 Host API 或允许其他发行方是另一次显式协议/风险评估。

## 5. 安装、更新与失败恢复（目标语义；#27 已验收调查，不等于机制已证明）

首版对外目标路径：`未安装 → 接收/暂存 → 检查签名/摘要/兼容/资源 → 提交已安装版本 → 管理员手动执行 → 返回或报告故障`。更新必须先完整验证候选包，不能先破坏旧版本再决定其是否可信。

用户可观察的最低一致性规则：

- 接收中断、验签或兼容失败：不得新增可执行的半包，不得改变已安装的有效版本。
- 安装/升级提交异常或重启：恢复后必须是**旧版本或完整新版本**的明确可判定状态，不能把不完整包当作可执行安装；旧版是否需要在成功提交后保留，需根据容量与事务机制定案。
- 空间不足、写入失败和重复请求：返回可解释的失败/结果，不覆盖其他 App 或用户数据；具体幂等键/重试细则待定。
- 卸载：移除该 App 的可执行/管理元信息，不误删其他持久数据；首版无 App 私有存储 API，未来应用数据清除/保留属于新版本协议，不应被臆造。
- 切勿为 App 安装改写 FSBL、APP1/APP2、OTA 信息、基础 Web、AI 分区或任意未明确授权持久区。

### 5.1 安装/升级/卸载的失败结果矩阵（A 候选验收语义；非实测）

| 场景 | 对外允许结果与数据不变量 | 禁止的假成功 |
| --- | --- | --- |
| 从未安装：上传中断或坏包 | 保持 `not_installed`；暂存物不得被执行 | 上传了一部分就显示 `installed` |
| 已安装 V1：上传/验证 V2 失败 | 有效 V1 及其可查询身份不变；V2 不得执行 | 用坏 V2 覆盖已提交 V1 |
| V1→V2 提交中断/掉电 | 重启后可验证地指向**完整 V1 或完整 V2**之一；失败/恢复原因可查询；无不完整可执行版本 | 只剩半包、版本记录与镜像不一致或静默删除原始数据 |
| 无空间/碎片化/存储读写异常 | 在保证旧有效数据/既有其他文件安全的前提下拒绝提交；必要时进入不可执行的受控故障状态 | 因 mount 失败自动格式化整个共享用户卷并报成功 |
| 同身份、同版、同包摘要再次安装 | `already_installed/no_change`，不得产生不必要的版本切换 | 将重试伪装成一个不同的成功新版本 |
| 同身份同版本而包摘要不同 | `VERSION_CONTENT_CONFLICT`，原安装状态不变 | 静默覆盖而无法解释版本来源 |
| 已安装版本高于候选版本 | `DOWNGRADE_FORBIDDEN`，除非未来明确受权的恢复协议 | 用签名正确作为允许降级的理由 |
| 新设备/Host 的目标或 ABI 不匹配 | `TARGET_INCOMPATIBLE` / `ABI_INCOMPATIBLE` / `RESOURCE_LIMIT`；不可执行；先前可用版本不被静默替换 | 忽略 manifest/镜像头冲突 |
| 当前正在运行 | 第二次运行、更新、卸载以 `BUSY` 拒绝；不假设可安全强制终止 | 写入或卸载运行中执行镜像，或假报停止成功 |
| 管理员卸载后或重复卸载 | 卸载提交成功后该身份不可执行；重复卸载返回无变更；其他 App/用户数据不变 | 删除了普通文件就断言已撤销所有执行入口 |
| 重启、信任撤销或 Host 不再兼容 | 从可信持久安装记录恢复身份，再决定 `installed` 或 `unavailable`；**不自动运行** | 自动运行失信/不兼容代码，或隐匿记录丢失 |

“旧版本或完整新版本”是 **P4 必须证明的产品 AC**，不是 LittleFS rename、文件删除或 #2 离线注入已经提供的事实；如果设备路径无法达到该结果，A 应暂停/重新规划 P4，而非放宽为“通常能成功”。严格保留现有 `/captures`、日志、配置等共享用户数据，备份丢失也不能被伪装成成功回退。

**已核实的风险与尚未完成的证明**：#27 的 [受审调查报告](https://github.com/harryhua-ai/ne301/blob/b00584d598628ebeefdd95bbb6c43ffd4477f412/Docs/design/app-install-feasibility.md) 确认当前 LittleFS mount 失败时有静默格式化路径；#2 的 4KiB 小段 SWD 写/编程器 64KiB 擦除重叠事故曾触发数据丢失，96MiB 全卷恢复后经内容清单验证，但**不能**据此推断固件运行时的掉电行为。旧 counting APP1 有备份但实际恢复未测试，APP2/OTA 切槽仍是未证备选，关键备份只在 `/tmp` 单副本。P4 只能把经独立证明、设备现存数据保护边界内的文件区域作为 App 候选存储；不得复用 APP1/APP2 或单槽 WEB/AI/FSBL。安装事务必须保留旧有效版本直至新版本可确认提交，且 mount/写入异常不能静默抹掉用户其他数据。**实现此目标需要重新设计或拦截现有危险恢复路径并经专门验证，现有文件 API 不提供产品安装事务证明**。在批准任何板卡写入前，必须有可持久保存、完整核对的独立备份与真实可行的回退路径；否则只允许静态/离线验证，不得冒称 AC 通过。

## 6. 执行生命周期（已确认边界 + A 候选语义）

- 唯一首版入口是管理员显式发起的一次性执行，Host 校验当前已安装镜像的完整性/兼容性并以既定 ABI 调用；执行结束记录结果码/可取得的日志。**重启后默认不自动运行**。
- V1/V2 的执行必须证明两个独立产物在同一 Host 上替换运行，且主固件/基础 Web 前后不变。实验 #2 已证明的只是 UART 命令 + LittleFS 注入实验路径，不能代替 Web 安装验证。
- 不能承诺原生代码的抢占式安全停止、运行超时杀死、内存隔离或崩溃后主系统存活；这些属于尚无证据的能力。异常后的状态恢复、执行中更新/卸载的禁止/等待规则须在设备边界清楚后明确，不得默认并发安全。

## 7. 面向 P3/P4/P5 的错误与证据接口（A 候选语义）

对外至少区分 `AUTH_REQUIRED`、`FORBIDDEN`、`BAD_PACKAGE`、`SIGNATURE_INVALID`、`PUBLISHER_UNTRUSTED`、`TARGET_INCOMPATIBLE`、`ABI_INCOMPATIBLE`、`RESOURCE_LIMIT`、`STORAGE_FULL`、`COMMIT_FAILED`、`RUNTIME_UNAVAILABLE`、`BUSY`、`DOWNGRADE_FORBIDDEN`、`VERSION_CONTENT_CONFLICT`。权限与验签检查失败不得切换已安装版本或暴露攻击者可利用的密钥/内部错误信息。枚举值/HTTP 映射及记录恢复中状态仍待最终协议冻结；不得把上传成功、签名通过或后台文件已存在误报为安装成功。

### 7.1 请求结果与状态优先级（A 候选语义）

- **认证优先**：未通过管理员授权的上传、查询敏感包信息、安装/升级/卸载和运行请求一律拒绝，不向未授权调用者泄露已安装发行者、公钥细节或包解析细节。管理员授权通过后，仍须独立验证设备信任锚与包签名；有文件读写权限不等于获准执行。
- **验证不是提交**：上传/暂存成功、包结构解析成功、签名通过、兼容检查通过是不同操作结果；只有持久提交被证明成功才能返回 `installed` 与有效身份/版本/摘要；返回结果必须使 Web 可区分“失败但旧版仍有效”“未知/不可信不可运行”“已成功升级”。具体 HTTP 状态码/传输 JSON 字段、原始错误枚举的数值和长度限制待 wire/API 规范冻结。
- **错误至少覆盖**：认证/授权、包结构、签名失效/未知发行者、设备/ABI/资源不兼容、版本冲突/降级、运行忙、存储容量/提交失败和运行不可用。可能有多个错误时不保证客户端看到每一种原因；对外保证返回稳定且不泄露密钥或内部路径的**主分类**，并保留仅管理员可审计的有效版本与必要操作记录。
- **手动运行结果不得混同安装结果**：正常返回的 App 返回码与加载器的系统错误是不同数据；当前实验入口返回值经包装，不能臆造崩溃可恢复的执行结果或长期运行状态。发生设备异常/不可证明运行状态时，管理 API 不得假报成功。

拟冻结的跨仓库验收场景：可信 V1 安装与手动运行；同 Host 下可信 V2 替换；篡改 manifest/payload 或错误签名/不可信发行者拒绝；错误板型/ABI/大小拒绝；普通用户和未认证者拒绝；写入失败/容量不足/断电重启后完整旧/新状态；卸载后无法再运行；主固件与基础 Web 未发生 App 替换写入。这些是协议证据期望，**不代表任何场景已在 P3/P4 实测**。

### 7.2 P4 READY 前安全与数据保护验收门槛（A 决策约束）

以下是**P4 在获得新实施授权前必须可证实的条件**，不是指当前 NE301 已满足，也不将单个 AC 扩展为不相关生产安全认证。

| 风险边界 | 最低需要的证据 / 结果 | 不满足时 |
| --- | --- | --- |
| **可信入口** | 安装与执行入口不能通过普通文件上传、调试 UART 或已有不验签 OTA 路径绕过产品 App 验签与授权；受控实验 Host 的身份、入口与信任根配置可重现 | 只允许离线/隔离原型，不宣称“可信安装” |
| **管理员管理权限** | 证明管理接口受认证授权；#27 已指明密码明文日志及存储/哈希缺口，A 必须明确这些缺口的修复/隔离条件，不能依靠现有会话存在来推定安全 | 暂停生产可触达的安装入口；按风险拆出独立安全整改任务 |
| **签名与信任根** | 设备端验签真正执行、发行者映射不可由上传数据授信；测试涵盖被篡改包/错误密钥/不支持板型；#32 离线验签能力经 A 验收后再决定算法 | 不发 P3/P4 签名相关 READY |
| **原生代码权限** | 明示已验证的 trusted-native-only 威胁模型；不宣称特权代码的沙箱、独立崩溃恢复或凭据隔离 | 限定受控发行方及隔离验证，不开放不可信生态 |
| **持久化与掉电** | App 版本提交、卸载、重启/断电/满盘等经适当的独立故障场景验证；读写失败不会静默格式化共享用户数据；旧版/完整新版状态可复核 | P4 #30 不可宣称 AC 通过，不以“正常路径可用”代替 |
| **开发板与回退** | 确认当前开发板真实固件与用户数据；备份可耐久保存、逐项校验且恢复路径可执行；未经单独受权不进行破坏性设备实验 | 保持只读/离线，禁止写板 |
| **跨仓库一致性** | P3 生成器和 P4 验证器使用唯一已集成版本规范及相同黄金/反例向量；主固件与基础 Web 仍为未被 App 替换写入的受保护对象 | 不得进入端到端或对外发布验收 |

**验收分层**：#27/#32 只读调查可以关闭“有什么能力/缺口”的证据问题，不能关闭“设备已实现安全安装”这个产品结果；#29 接受验证与准入、#30 接受持久事务/失败恢复、#31 接受手动运行，三者组合后仍须另行验证联调和实际 Web 用户流程。高风险真机写入的独立授权不能从 GitHub Issue 的 `ready` 或过去实验成功中推定。
